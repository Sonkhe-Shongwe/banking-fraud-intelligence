# Banking Fraud Intelligence project instructions

1. **Restore context first.** At the start of a session, verify the GitHub repository, active branch and exact HEAD. Read the documentation index, current handoff, project scorecard, and any task-specific design, data or methodology records. Do not assume the owner's local checkout matches GitHub.
2. **Respect approval boundaries.** Research, audits and non-binding proposals may be prepared for review. Do not implement unapproved dashboard design details or make consequential changes to scope, architecture, schedule, publication exposure or verified workflows. An approval applies only to the specific decision or operation accepted.
3. **Use the safe-change cycle.** Before a meaningful change, define its objective and acceptance checks; assess failure modes, likelihood, impact, prevention, detection and recovery; identify required approval; then make the smallest reviewable change. No process is fail-proof, so state residual risks honestly.
4. **Protect owner work and repository history.** Inspect the branch and working tree when available. Never silently stash, discard, reset, clean, overwrite or relocate owner files. Never force-push. Re-check the expected remote HEAD before publishing, review the exact changed-file list, and stop to reconcile unexpected concurrent changes.
5. **Verify what actually ran.** Distinguish repository inspection, local Windows execution, Python notebook/script execution and Power BI Desktop behaviour. Record the commit, input revision, environment, commands and observed results. Do not claim an application check passed from code inspection alone.
6. **Preserve data and analytical integrity.** Keep raw data, processed extracts, transaction-level exports and credentials out of Git unless an explicit documented approval permits otherwise. Preserve source manifests, scoring-time constraints, chronological evaluation and honest simulated-data language.
7. **Maintain continuity and evidence.** Work in small increments. Update the handoff when the verified checkpoint or next action changes, and update the scorecard only when acceptance evidence changes. Keep the documentation index and README aligned. Report the commit, verification, remaining risks and the exact action the owner should take.
8. **Resume from the source of truth.** For a new conversation, use the [master continuation prompt](docs/MASTER_CONTINUATION_PROMPT.md), then verify the latest handoff and scorecard before acting.
